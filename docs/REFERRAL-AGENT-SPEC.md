# IPZSK 推广分佣｜Agent 研发交接与验收约束

> 版本：v0.1，内部交接稿；状态：**产品规则已讨论，代码实现及生产状态未核验**。
>
> 上游业务文件：[REFERRAL-PRD.md](./REFERRAL-PRD.md)。本文是给研发／测试 Agent 的可执行交接，不是独立创造规则的权限。发现冲突、未决字段或代码现实与文档不符时，输出差异并等待产品确认，不以猜测填充。

## A．任务和权限边界

目标是在当前真实账户、支付、充值账本之上增加**一级直接推荐、统一 5% 的充值佣金**。不得自行增加多级、团队奖励、自动阶梯、代理门槛、老用户补绑、佣金复投返佣或自动外部打款。第一版运行满 3 个月后才讨论比例变化；不要预先实现 6%～10% 自动升级。

可先做代码和数据审计、差异清单、测试计划；修改生产资金、收款账户、法律条款或对外上线前，应先有人确认。尤其不能把过时的 `docs/DEPLOYMENT.md` 当作现行代码和支付链路。不得从共享聊天中的“已部署／已配置”直接推断本仓库或线上状态。

## B．项目事实分层

| 类型 | 当前能确认什么 | Agent 的动作 |
| --- | --- | --- |
| 已决定的产品规则 | 人人自动拥有链接；注册时使用的链接绑定唯一直接推荐者；绑定关系长期保留；每笔有效实付充值按 5% 计佣；30 天观察；月结；现金提现最低 ¥100；可选择转使用额度；异常订单可核查取消。 | 按这些规则设计并验证。 |
| 外部支付约束 | Waffo [条款](https://www.waffo.ai/en/developer-terms)仍允许退款／拒付及结算调整；30 天后不是外部支付的不可逆保证。 | 保留逆向账务事件，不把 `archived` 当成支付不可撤销。 |
| 未核验的工程事实 | 实际账号系统、现行支付渠道、Waffo 生产权限、Webhook、佣金或钱包表、部署拓扑。 | 先查当前仓库与可访问的环境；逐项报告证据和未验证处。 |
| 未决业务参数 | PRD 第 8 节的 URL、舍入、部分退款、转换比例、打款日、收款渠道／费用／税务等。 | 标记为 `BLOCKED_PRODUCT_DECISION`，不可默默定默认值并上线。 |

## C．不变量

用这些约束检查任何实现，不依赖推荐链的深度：

```text
referrer_of(user) = 注册提交时所用的有效推广链接所属用户，或 null
referrer_of(user) 一旦确认，普通用户操作不得改变
referrer_of(user) != user
commission_recipient(order) = referrer_of(order.payer_user_id)
仅付款者的直接推荐者可取得佣金；不遍历祖先关系、不向祖先另发佣金
commission(order) = eligible_net_paid(order) × 0.05 [舍入待确认]
commission(赠送额度／佣金转额度／使用额度扣费／测试单) = 0
一笔外部支付订单最多创建一笔原始佣金；每个退款／拒付事件最多执行一次冲销
```

“注册时使用的链接”优先于此前曾访问的其他人的链接。A 链接→B 链接→通过 B 链接注册，归 B。没有成功注册时不建立关系。已注册用户点任何链接都不换绑。若当前前端无法可靠把注册链接传至服务端，应先报告归因能力缺口，不用浏览器展示值代替服务端持久记录。

“终身绑定”是账户间**直接归因边**；任何报表和计佣查询只取付款者的 `referrer_id` 一跳。A→B→C 时，即使数据库能遍历整条路径，也不能把 C 的付款计入 A 的佣金、等级或团队业绩。

## D．建议的最小数据契约（字段名可随现有架构调整）

在审计现有模型后复用现有 `users`、充值订单和余额账本，不为本功能重复造一套用户／充值系统。逻辑上至少需要：

| 逻辑记录 | 必备信息与约束 |
| --- | --- |
| `referral_identity` | `promoter_user_id`、唯一不可猜测的 `referral_code`、创建时间、状态；每个注册用户一份。链接自动生成；不要把 code 当作充值兑换码。 |
| `referral_attribution` | `referred_user_id` 唯一、`promoter_user_id`、注册时间、使用的链接／码、归因证据、规则版本；普通操作不可更新。管理员异常更正需审计日志且不静默重写旧账。 |
| `commission_ledger` | `id`、`promoter_user_id`、`payer_user_id`、外部 `payment_order_id`、订单实付／税费／可计佣基数（人民币整数分）、佣金整数分、`rate_bps=500`、事件类型、状态、事件时间、规则版本、幂等键；保留正负流水，不以余额覆盖历史。 |
| `commission_account` | 待结算、可结算、已申请提现、已打款、已转使用额度、待追回等汇总可由流水重建；并发提现或转换不能超支。 |
| `payout_or_conversion` | 选择的金额、人民币记账额、收款方式或转换目标、状态、申请／处理时间、操作人、付款／转换外部凭证、唯一幂等键。现金和额度两条分支互斥消耗同一可结算佣金。 |
| `review_audit` | 异常触发原因、证据引用、暂停范围、处理决定、处理人、时间、通知／申诉记录；不得只存一个无原因的“取消”标志。 |

收款姓名、地区及账号只在用户申请现金提现时收集；将完整账号限制在授权后台或支付渠道，普通推广 dashboard 不返回。金融账户信息处理遵循[个人信息最小必要要求](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)。

## E．事件流与状态

```text
注册成功
  → 若注册请求携带有效链接且是新账户，写入唯一归因
  → 为该新账户自动生成自己的推广链接

已验证的真实付款事件（不是浏览器成功页）
  → 核对环境／外部订单 ID／支付状态／付款账户／金额／税费
  → 原充值账本完成唯一入账
  → 若付款者有直接推荐者，创建唯一 pending 佣金流水

pending
  → 满 30 天、对账完成、无已知退款或争议 → available
  → 退款／拒付／确认异常 → reversed 或 review_hold（保留原流水）

available
  → 月度现金申请且金额 ≥ ¥100 → payout_requested → paid／failed
  → 用户选择转使用额度 → conversion_requested → converted／failed
  → 后续退款／拒付 → reversal／receivable（已支付时记待追回）
```

每一步需要事务或等效的原子保证：重复回调不重复计佣；结算任务重复执行不重复释放；并发提现和转换最多成功一笔；失败请求不得消耗可结算金额；转换使用额度和扣减佣金余额同一业务操作关联。所有金额以整数分存储。舍入、部分退款和币种换算未确认时不发布相关资金路径。

观察期与打款周期是两件事。满 30 天只是转 `available` 的条件；实际打款按月处理。`archived` 若存在，只能映射为内部对账／可结算状态，不能屏蔽之后收到的支付通道撤销事件。Waffo 或其他支付服务商是否提供具体事件、回查接口与真实资金状态，需对当前生产环境逐项验证。

## F．接口与界面职责，不预设路由名

- 推广中心：获取本人的链接、直接有效注册／付费统计、本人佣金流水、待结算／可结算／已处理金额；不得查到间接客户或被推荐人的个人资料、生成内容。
- 注册：服务端接收并验证这次注册使用的推广链接身份；一次写入唯一推荐关系。跨设备、登录已存在账号、注册失败重试的行为依 PRD 第 8 节补充。
- 提现：展示最低 ¥100 和可用金额；收取必需收款资料；申请后进入月度审核／打款。Starryblu、Wise、境外银行尚属候选，不要硬编码为已可用渠道，也不要假定 Waffo 能代付推广者。
- 转使用额度：仅针对可结算佣金，禁止转换再次计佣；转换比例及金额门槛在产品确认前只做接口／状态预留，不上线资金变动。
- 管理后台：订单级归因、支付验证、退款／拒付、异常暂停与审核、月度对账和打款凭证；所有人工更改留审计轨迹。

## G．验收用例（先写测试，再核对实现）

| ID | 输入／动作 | 必须结果 |
| --- | --- | --- |
| R-01 | A 分享给 B；B 分享给 C；B 和 C 各有效实付 ¥100 | A 只得 B 的 ¥5；B 只得 C 的 ¥5；A 对 C 得 ¥0。 |
| R-02 | 未注册访客先点 A，之后通过 B 链接注册；再点 A | B 是唯一推荐者；后续点击不改变。 |
| R-03 | 已有账户打开 A 的链接并充值 ¥100 | 不因这次点击建立新归因或给 A 佣金。 |
| R-04 | 真实订单 ¥100；相同支付成功事件重复到达两次 | 原充值和 ¥5 待结算佣金各只有一次。 |
| R-05 | 新用户领取赠送额度／使用额度生成图片／推广者把佣金转额度 | 三种操作都不产生新的推广佣金。 |
| R-06 | 有效 ¥100 订单已过 29 天；第 31 天对账正常 | 第 29 天仍待结算；第 31 天可结算，但不是支付不可撤销。 |
| R-07 | `available=¥99.99`，申请提现 ¥100；随后 `available=¥100` 再申请 | 第一次拒绝；第二次在资料完整且无冻结时才进入申请流程。 |
| R-08 | 同一笔 ¥100 可用佣金并发提现与转额度 | 最多成功一条分支，另一条不得导致负余额或重复领用。 |
| R-09 | ¥100 订单被部分／全部退款；或打款后出现拒付 | 留存原佣金，生成对应负流水；已打款的产生待追回记录。部分退款舍入预期需先确认。 |
| R-10 | 推广者被异常标记／复核 | 只暂停相关佣金，保留证据与审核轨迹；无证据不直接永久抹账。 |

除自动测试外，需对真实支付沙箱做支付成功、重复通知、退款、争议、对账、月结和打款失败的端到端验证。沙箱通过不等于生产收款和跨境打款已验证。

## H．交付与变更

研发开始时先提交一页**现实差异清单**：当前代码位置、当前支付渠道及环境、已有钱包账本、已存在的相似表与接口、与本文冲突的旧需求、测试覆盖和未获确认的产品决策。之后才给出最小改动实施计划；不要为了“完整”新增不必要的层级、数据同步或审批系统。

每次评审或实现改动都更新本文件与人类版的对应条目，并记录变更日期、原因、批准者、版本、是否影响既有订单与补测结果。状态至少区分 `draft`、`reviewed`、`implemented`、`tested`、`deployed`、`live_verified`；不得把文档写好或本地测试通过表述为已经上线。
